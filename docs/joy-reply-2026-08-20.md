## A. What I need from you

Six items. The first two block specified behaviour; the rest are friction.

### A1. `POST /sessions` cannot reopen a session — **blocks the core loop**

This is the important one. `POST /sessions` is create-only and nothing reads a
session back, so the two kinds fail in opposite directions:

| | what happens | consequence |
|---|---|---|
| **Task session** | `409` — *"that task already has a session"* | Tapping a task row **cannot open its session at all**. That is §5.3, the loop the whole architecture is built around. |
| **General session** | `200`, but a **new** session each launch | Chat loses its entire history on every app restart. Verified: two launches, two ids, second one empty. |

Both break acceptance §12.8 — *"kill the app mid-refinement; reopen; session
resumes with history intact."*

**The app cannot work around either.** There is no `GET /sessions`, no
`GET /tasks/{id}/session`, and the 409 body carries no session id — so once a
session exists the app has no way to name it again.

Simplest fix, and what "one session per task" already implies:

```
POST /sessions {kind:"task", task_id:12}  -> 200 + the existing session, not 409
POST /sessions {kind:"general"}           -> 200 + the one general session
```

`agent.sessions.task_id` is already unique, so the task case is
upsert-and-return rather than insert-or-conflict. The general case needs a rule
for what "the" general session is — most recent, or a singleton row. A
`GET /sessions?kind=&task_id=` lookup would serve equally well; the app is happy
with either.

*Everything else in this document was verified around this hole — I tested the
proposal and confirm flow through a new unbound session, which does not 409
because no session exists yet.*

### A2. `find_tasks` needs date ranges — a stated requirement

Asked *"what's due today?"* live, the agent replied it has no way to list tasks
or filter by due date, and offered a keyword search instead. These are confirmed
real use cases, in the user's own words:

- *"What's due today?"* · *"What's due this week?"* · *"What's due in the next 3 days?"*

**The query already exists.** `GET /tasks?date_from=&date_to=&status=` is what
the Tasks tab pages through. Nothing new in the schema or the data — the same
predicate needs exposing as a tool the model can call in a general session:

```
find_tasks(query?, date_from?, date_to?, status?)
```

A filter chip cannot replace this. The tab offers Today / Next 7 days / Overdue;
*"the next three days"* is not on that list and cannot be, because a chip row
cannot enumerate every window somebody might ask for. Open-ended ranges are what
chat is *for*.

> **One trap worth stating.** The model must **not** compute those dates. "Today"
> is the user's local calendar day, the server runs UTC, and a model left to work
> out "the next three days" will use whatever it thinks the date is —
> reintroducing the local-day bug in the one place there is no `due_date` field
> to fall back on. Either resolve the range server-side inside the tool, or
> inject the user's local `today` into the prompt as an anchor. The app
> deliberately has no say: it never computes a task's day and should not start.

### A3. No route redeems a `task_options` cursor — blocks "Show more"

`task_options` carries `more_cursor`, and §5.4 specifies buttons three at a time
with "Show more" paging the rest. No route accepts that cursor. Redeeming it
through `POST /messages` would mean inventing a fake user turn — it would appear
in the transcript as something the user said, and spend a model call to page a
list you already have.

The app currently fails that tap with an honest message. Disambiguation works up
to three candidates; beyond that it is blocked. A `GET /sessions/{id}/options?cursor=`
would close it.

### A4. There is no `GET /tasks/{id}`

Opening a task session needs that one task, to know whether it is terminal and
therefore whether the composer appears. With no single-task route the app pages
`GET /tasks` until it finds the id — twenty rows fetched to read one, and worse
for a task deep in the list.

### A5. Mutation responses are untyped in the schema

`PATCH /tasks/{id}`, `POST /tasks/{id}/cancel` and `POST /proposals/{id}/confirm`
are declared as bare objects with no schema — no FastAPI return annotation —
while §4.4 says they return `{task}`. The app reads either an envelope or a bare
task so a later annotation cannot break it, but that is a guess wearing a
seatbelt. Annotating them would settle it and let the app drop the tolerant
decoder.

### A6. `status` on `GET /tasks` takes one value

Not blocking, and the app now matches it — the filter chips became single-select,
because a row offering "Active + Missed" while you can only answer one of them is
a filter that silently means something other than it shows. If repeated params
are cheap (`status: list[str] | None`), the chips go back to multi-select.

## C. Your two re-read items

Both taken, and one needs a correction.

### C1. `due_at` is `date-time`, `due_date` is `date`

**Already correct, and structurally enforced.** The app has never modelled these
as the same type:

```kotlin
@Serializable(InstantSerializer::class)
@SerialName("due_at")   val dueAt: Instant       // exact instant

@Serializable(LocalDateSerializer::class)
@SerialName("due_date") val dueDate: LocalDate   // bare local day, display key
```

`LocalDate` has no time and no zone, so the mistake you are warning about is not
expressible — deriving a display day from `dueAt` would require writing a zone
conversion that does not exist anywhere in the app. There is a unit test that
fails if the two ever agree on the boundary case.

### C2. The local-day test — you are right about the plans, wrong about my test

Your correction to the **plans** is right and worth propagating: Sydney is UTC+10,
so a 9 PM reminder lands at 11:00 UTC the *same* day. The plans' example is
backwards; only the morning crosses.

But the test does not need changing, because it was built from the arithmetic
rather than from the plan's example. It uses **8 AM Sydney**:

| | UTC day | Sydney day | exercises the bug? |
|---|---|---|---|
| 9 PM Sydney *(the plans' example)* | 21 Aug | 21 Aug | **No** — passes either way |
| 9 AM Sydney *(your suggestion)* | 20 Aug | 21 Aug | Yes |
| **8 AM Sydney *(what the test uses)*** | 21 Aug | 22 Aug | **Yes** |

`due_at: 2026-08-21T22:00:00Z` with `due_date: 2026-08-22` — 22:00 UTC plus ten
hours is 08:00 the next day in Sydney. Morning, and it crosses.

I have added an assertion that pins the fixture to the crossing direction, so it
cannot quietly stop testing anything if someone edits the date later. **Please do
not "correct" the app plan's test spec toward 9 AM as though the current test were
wrong** — it would be churn on something already right. Correcting the §3 prose
example is worth doing.
