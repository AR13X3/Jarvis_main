## Implemented from your handoff

### 1. `status` on the confirm component — done

```jsonc
{ "type": "confirm", "proposal_id": "…", "status": "pending", "summary": { … } }
```

One thing to rely on: **`status` is refreshed from `agent.proposals` on every
read, never replayed from the stored snapshot.** A card written while pending and
confirmed later reports `confirmed` when you scroll back. Your default-to-pending
fallback is still correct for older rows, but it will not be exercised.

### 2. Message shape — done, and it is now in the schema

```jsonc
{ "messages": [ { "id": 41, "role": "user|assistant|tool",
                  "text": "…", "components": [ … ],
                  "created_at": "…" } ],
  "has_more": true }
```

Your assumption is what shipped, including `components` on persisted assistant
turns (new `agent.messages.components` column, migration 0003). The field is
`text`, not `content` — the plan never specified this shape, so yours won.

Note `role` can be `tool` in the enum, but **tool turns are never returned** —
they are machinery, not conversation, and would leak the tool loop into the
transcript.

### 3. Cancel scope — done

```
POST /tasks/{id}/cancel { "confirm": true, "scope": "occurrence" | "series" }
```

`occurrence` resolves the current firing and advances `next_fire_at`; `series`
sets the task `cancelled`. Absent `scope` defaults to `series`, as you proposed.

Settled alongside it: **`complete` always means this firing** and takes no scope,
since completing a whole series early is really cancelling it. So
`propose_complete` needs nothing from you.

### 4. Section queries — taken as specified, and you caught a real bug

Your queries shipped verbatim. The `status = 'active'` subtlety was a genuine
defect: a fired recurring task left Recurring and reappeared under Priority still
captioned "Every Sunday". **Recurring is a property of the rule, not the current
occurrence.** There is now a regression test asserting a fired repeating task
stays in Recurring and does not appear in Priority.

**"All tasks" keeps listing everything**, including rows shown above it. Decided
deliberately: highlights above, full paged list below. Unlike two peer sections
that reads as intentional, and a starred task should not vanish from the main
list when you star it.

### Two bugs found here that may matter to you

1. **`due_at` with sub-second precision silently ate the first occurrence** of
   every recurring task — `dateutil`'s rrule works at second resolution, so an
   anchor with microseconds sorts after its own first occurrence. Fixed. If you
   ever construct a due time client-side, truncate to whole seconds.
2. The **timezone example in both plans was backwards.** Sydney is UTC+10, so it
   is the **morning** that falls on the previous UTC day
   (`09:00 Sydney = 23:00 UTC the day before`), not the evening. Your local-day
   test should use a **9 AM** task — a 9 PM one passes whether the code is right
   or wrong. §3 and the test spec in the app plan are corrected.

## What I rely on from your guarantees

All six are exactly what the server assumes, in particular: no tool list from the
client, no RRULE parsing, and no client-side `due_date` / `due_today`. The
unknown-component fallback is genuinely useful — it means new component types can
ship server-side without waiting on an app release.

One request: `due_at` is `format: date-time` and `due_date` is `format: date` in
the schema. **That type difference is the local-day rule.** If a DTO makes both
`Instant`, the highest-risk bug in the system is back.
