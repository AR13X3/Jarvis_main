## The asks

### Ask 1 · `POST /sessions {task_id}` — **done, verified**

Bound sessions are now get-or-create. Posted the same `task_id` twice against
the live gateway and got the same session id back both times, no 409:

```
POST /sessions {"kind":"task","task_id":21}  ->  200  d9b74d24-…
POST /sessions {"kind":"task","task_id":21}  ->  200  d9b74d24-…   (same)
```

Reopening does **not** touch `updated_at` — the insert conflicts and re-selects
rather than updating, so opening a conversation does not count as activity. That
matters for the ordering in ask 3 when it lands.

**Only the bound case is idempotent.** Your correction was right and is what
shipped: an unbound `POST /sessions` still opens a new session every time,
because that is what starting a conversation is.

### Ask 2 · `find_tasks` date ranges — **done**

The tool takes `due_range` (`today` | `tomorrow` | `overdue` | `next_days`) plus
`days`, and **the server resolves it**. The model is never given date arithmetic:

```
today            -> 2026-08-20 .. 2026-08-20
tomorrow         -> 2026-08-21 .. 2026-08-21
next_days, 3     -> 2026-08-20 .. 2026-08-22
next_days, 7     -> 2026-08-20 .. 2026-08-26
overdue          -> .. 2026-08-19, and still unresolved
```

Resolution runs off the user's local calendar day, not UTC — your trap is
handled where you asked for it to be. The tool description tells the model in as
many words never to work dates out itself. `overdue` deliberately means *past
and still open*, so a task completed last week is not overdue.

Verified at the resolver, not yet through a live model turn.

### Ask 6 · mutation return types — **done, with one caveat you should read**

`PATCH /tasks/{id}`, `POST /tasks/{id}/cancel` and
`POST /proposals/{id}/confirm` are annotated `TaskEnvelope` — `{"task": …}` —
and appear as a named schema. Verified live: `PATCH` returns `{"task":{…}}`.

**Keep your tolerant decoder on `confirm` for now.** `TaskEnvelope.task` is
declared non-nullable, but the confirm path can in principle produce a null task
— it resolves a proposal by id, and the underlying update returns nothing if the
task row has gone. It is near-unreachable, because rows are never deleted here,
but the annotation currently promises more than the code guarantees. We are
tightening that end rather than loosening the schema; until the next contract,
`confirm` is the one place the envelope could lie. `PATCH` and `cancel` are
safe.

## Your phase-E questions — both answered by measurement

**1. Does `/occurrences/upcoming` include one-shot tasks?** **Yes.** Checked
against live data: of the three occurrences currently in the window, two belong
to one-shot tasks (`Water the plants`, `Go to the gym`, both `recurrence` null)
and one to a weekly rule (`Take the bins out`, `FREQ=WEEKLY;BYDAY=MO`). Every
task gets an occurrence — a one-shot gets exactly one — so the scheduler, the
due-today indicator and this endpoint all read from one place. You will not have
to find that out the hard way.

**2. Is the window measured from `now` at request time?** **Yes, request time,
not midnight.** The predicate is `scheduled_for >= now() and < now() + interval`.
Two calls three seconds apart returned `generated_at` 12:32:06 and 12:32:09.
Your replace-the-window approach is the right one against a moving anchor.

## One thing to know before you build phase E

We found and fixed a bug that would have hit you directly, and **you would have
been blamed for it.**

Rescheduling a task inserted a new occurrence without resolving the one it
replaced, leaving two rows live. `/occurrences/upcoming` returned both, so a
moved reminder would have armed **two alarms** — the old time and the new one.
Your replace-the-window logic was correct throughout; it would have faithfully
armed exactly what we sent.

Fixed at the write path, but the fix did not clean up rows already wrong. **This
window was still serving a duplicate as of an hour ago** — `Go to the gym` was
being offered at both 13:00 and 13:30. That stale row is now cancelled and the
window is one alarm per task:

```
task 21  Go to the gym       2026-08-21T13:30:00Z
task 18  Take the bins out   2026-08-23T21:00:00Z
task 15  Water the plants    2026-08-24T22:00:00Z
```

Worth knowing because it means anything you measured against this endpoint
before now may have been counting a phantom.

Related and also fixed: `GET /tasks` returned **500** for an unknown `status`,
and both date filters returned 500 for *every* value including valid ones — they
had never worked. All now 422 in FastAPI's standard shape.
