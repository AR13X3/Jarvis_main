**Why it matters to you even though the wire format is unchanged.** Both forms
mean the same request — `Authorization: Bearer <GATEWAY_TOKEN>`. But your copy
declares that header **optional on every endpoint**. Generate a client from it
and the token becomes an optional argument that compiles fine when omitted;
you would get a 401 that reads like a bad token rather than a missing one. The
new file makes it a security requirement the generator will enforce.

**Behaviour is unchanged and I verified it against the running service rather
than reasoning from the schema.** Missing header, wrong token, and wrong scheme
(`Token abc`) all return **`401 {"detail":"bad token"}`**, exactly as before —
`HTTPBearer` is configured with `auto_error=False` specifically so it describes
the auth without taking over the failure path. Your §8.2 error taxonomy stands
as written. There is no 403 anywhere in this gateway.

One deliberate quirk, so it does not look like an omission: **the file has no
`servers` block.** The gateway is mounted at `/api`, so the copy served at
`/api/openapi.json` does carry `"servers": [{"url": "/api"}]`. The file omits it
because your base URL already ends in `/api` and a generator that combines both

## 3. Please switch on OpenSSH Server on joy

Unrelated to the app — this is about not losing the data behind it.

`~/backups` on gw03 now covers the database *and* the receipt-photo storage
bucket nightly, with a restore that has been tested rather than assumed. It all
still sits on the same disk as the data it protects, so an `rm -rf` or a dead
disk takes both.

The off-machine half is built and tested here: it pushes to a second machine
over **sftp** (chosen because joy is Windows — rsync needs a binary on the far
side, sftp ships with the SSH server), verifies every file by pulling it back
and comparing SHA-256, and prunes the far side to the same 14 days. **joy has no
sshd listening**, so it cannot receive anything yet.

In an admin PowerShell:

```powershell
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
mkdir C:\jarvis-backups
```

Then authorise this key — generated for this one job, no passphrase:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIIdUzWR/CB0SN/ouLQIZLMicYEvrTAuvH5sFCM+Rn6W8 jarvis-backup gw03->offsite
```

Two things that make Windows SSH keys silently not work:

- An **administrator** account ignores `C:\Users\<you>\.ssh\authorized_keys` and
  reads `C:\ProgramData\ssh\administrators_authorized_keys`, which must have
  inheritance off and be granted only to `Administrators` and `SYSTEM`.
- The firewall rule the capability installs (`OpenSSH-Server-In-TCP`) is often
  scoped to private networks, and the Tailscale adapter usually is not one. If
  gw03 still times out on port 22, that is why.

Tell us the account name and we will finish the gw03 side.

**Worth saying plainly:** this puts the whole expenses and tasks history on joy,
unencrypted, on a machine that travels. Say so if you would rather it went
somewhere else — the target is one config line.
